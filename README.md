# Bridge Buddies (Unity WebGL)

The Unity WebGL build of Bridge Buddies, served from GitHub Pages as part of
[Little Joy Arcade](https://littlejoyarcade.site). This repository replaces the
Babylon.js build that previously answered for `bridge-buddies`.

- **Play:** <https://jd4rider.github.io/bridge-buddies-web/play/>
- **Cover page:** <https://jd4rider.github.io/bridge-buddies-web/>

## What is in here

```text
build/WebGL/                the untouched Unity WebGL export (61 MB, portrait 540 x 960)
scripts/prepare-site.mjs    turns that export into a Pages-servable site
site/                       generated by the script, not committed
.github/workflows/pages.yml prepare + deploy on every push to main
arcade-manifest.json        the catalogue entry for littlejoyarcade.site
```

There is no bundler, no framework and no dependencies. The only build step is
`prepare-site.mjs`, which needs nothing but Node.

## Why there is a build step at all

Unity's default WebGL export Brotli-compresses the payload (`*.data.br`,
`*.wasm.br`, `*.framework.js.br`) and expects the web server to answer with
`Content-Encoding: br`. GitHub Pages serves files as-is and gives you no way to
set response headers, so the browser would hand raw Brotli bytes to the loader
and the game would fail before the first frame with a parse error.

`prepare-site.mjs` therefore:

1. copies the export to `site/play/`;
2. expands any Brotli payload and points `index.html` at the plain files;
3. replaces the stock template's user-agent layout branch with one fit-to-screen
   rule, so the 540 x 960 play area keeps its 9:16 shape, letterboxes and centres
   on a desktop, and fills a phone;
4. fails the build if a required file is missing or if `WebGL.wasm` is not a wasm
   module, so a broken export is caught in CI instead of in a player's console.

This export already ships uncompressed files, so step 2 is a no-op today; it
still runs so a future compressed export deploys unchanged.

## Local development

```bash
node scripts/prepare-site.mjs
python3 -m http.server 8080 --directory site
# open http://localhost:8080/play/
```

Serve it over HTTP rather than opening the file — Unity's loader fetches the
payload and will not work from a `file://` URL.

## Updating the build

Re-export from Unity, then replace `build/WebGL/` with the new export and push:

```bash
rm -rf build/WebGL
cp -R "/Users/jonathanforrider/Developer/Bridge Buddies/Builds/WebGL" build/WebGL
git add -A && git commit -m "Update the WebGL build" && git push
```

Keep the export's compression setting on Brotli or Disabled; both work. Gzip and
`.unityweb` payloads are not handled by the script and fail the build with a
clear message.

## Platform integration

The export contains no `.jslib` bridge, so there is no sign-in or cloud save yet:
the Unity player keeps its own progress in browser storage, and the arcade
catalogue entry ships with an empty `saveKey`. The account/save integration is
described in `littlejoyarcade/UNITY_ACCOUNT_SAVE_BRIEF.md`.
